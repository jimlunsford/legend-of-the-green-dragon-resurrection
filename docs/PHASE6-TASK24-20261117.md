## 2. R11: what Jim saw

Jim's rc.3 server, 2026-11-17: a level 2 character with 10 forest fights. Pressing the new day's Continue gave the plain
409 "Forest combat unavailable. Stored state was preserved; reload for a fresh form, or request operator repair if it
remains invalid.", with no frame and no link.

## 3. Reproduction at `0632351`

Jim's path, played as a player plays it, in the web test harness on a fresh install (PHP 8.5, MySQL 8.4), forest events
off so the search is a fight:

1. The forest's page, then its search form: the posted search starts a fight (`badguy` stored).
2. The game day rolls over (`lastnewday` set to the day before).
3. The forest's search link, `forest.php?op=search&c=...`: 302 to `newday.php`. Task 23's rollover check runs
   `checkday()`, which keeps that address as the return page (`restorepage`).
4. `newday.php`, then its form: the new day, with one nav, Continue, made by `resurrection_newday_continue()` from the
   return page: the search link.
5. Continue: **409, the plain text above, with no link.** The fight is still stored, hitpoints and turns as the new
   day left them. The refused page kept nothing, so forced navigation sends the village and every other page to
   `badnav.php`, which replays the new day's page, whose only link is the same Continue.

The same happens after the new day for a player who was dead or had no hitpoints with the fight stored, and the new
test (a) and (b) below fail at `0632351` with exactly that 409 and text. A search with no forest fights left: the link
showed the search form (200) and its POST answered the plain 409.

## 4. The cause

Confirmed as the brief described. The search link while a fight is stored reaches `resurrection_forest_combat()`,
whose state check (`resurrection_forest_state(true)`) throws "Encounter already active"; the function's last catch
answered every `DomainException` with `http_response_code(409); exit(...)`, outside the game's frame and with no
navigation. Task 23 moved the rollover check before that state check, so the link began the new day, but the address it
left as the return page still led to the same refusal.

Found on the way, not changed: `forest.php` with no `op` shows the forest, as 1.1.2's did, even while a fight is
stored. Its test `httpget('op') === ''` never matches a missing `op`, because `httpget()` returns `false` for a missing
parameter, so the stored-fight route there fires only for `forest.php?op=`. That forest page offers the search links,
which is how a search link can be on screen while a fight is stored (for example the village's forest link after task
22's refusal, whose way back is the village). With this task those links show the stored fight. Making `forest.php`
itself show a stored fight would change what 1.1.2's forest page does; it is left for Jim to decide.

## 5. The fix

`lib/forest_combat.php`, `lib/specialty_combat.php`, `lib/web_security.php`. Every check and status code is kept.

- **A search while a fight is stored.** The search link (GET) shows that fight: the page `forest.php?op=fight` shows,
  the enemies and the fight's forms, with nothing spent or reset; the fight plays on. A posted search (after its CSRF
  check) is refused with task 22's framed 409 (`resurrection_refuse_action()`), whose one way out is back to the fight
  (`forest.php?op=fight`), made the return page. 1.1.2's search replaced the stored fight with a new encounter, so a
  search was a way out of any fight (a lost fight escaped for the cost of a turn); keeping the fight is the brief's
  choice and is kept.
- **A search with no forest fights left** (`resurrection_forest_tired()`): 1.1.2's text, "`$`bYou are too tired to search
  the forest any longer today.  Perhaps tomorrow you will have more energy.`b`0" (its `forest.php`, line 58), in the
  game's frame, then the forest (`forest()`, its description and navs), for the link and for a posted form (which must
  pass its CSRF check); no action token is spent and nothing about the player changes.
- **The forest's other refusals** (`resurrection_forest_refuse()`): 400 "Invalid Forest action.", 409 "Forest combat
  unavailable. ..." and 500 "Forest action was not completed. Request a fresh form." (still logged by `FailureLog`) keep
  their status and message, now in the game's frame through the new `resurrection_refuse_page()`, with one way out
  (`resurrection_forest_way()`): back to the fight while one is stored and valid, else the forest while the forest
  works for the player, else the village (the Shades for the dead). The way out is made the return page; only the
  navigation is written (`RESURRECTION_REFUSAL_PRESENTATION`), so whatever the refused request changed in the session is
  never stored. The Forest specialty round's three refusals (`resurrection_forest_specialty()`; its page
  `forest.php?op=specialty` can be a kept page) answer the same way.
- `resurrection_refuse_page()` (`lib/web_security.php`): the framed answer for a game page's refusal, with a title, a
  message and one way out; outside a game page (`resurrection_refusal_framed()`), or if drawing the frame itself fails,
  the plain text as before. `resurrection_refuse_action()` takes an optional way out in place of its way back to the
  village.
