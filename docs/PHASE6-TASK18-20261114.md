## Item 1 (F4): sign-in throttling

### What it does

`lib/signin_throttle.php` (new) and `login.php`:

| Limit | Counts | Window | Setting | Default | Bounds |
| --- | --- | --- | --- | --- | --- |
| pair | failures for one sign-in name from one address | 15 minutes | `signin_fail_pair` | 5 | 3 to 100 |
| address | failures from one address, whatever the name | 15 minutes | `signin_fail_address` | 20 | 5 to 1000 |
| account | failures for one sign-in name from every address | 1 hour | `signin_fail_account` | 50 | 20 to 1000 |

- **The count.** A failed sign-in is a `faillog` row: `post` the fixed word `invalid_credentials`, `ip` the requester
  key, `acctid` 0, `id` the sign-in name's key. The requester key is `resurrection_account_mail_requester()`, the one
  account mail uses: `REMOTE_ADDR` for IPv4, its /64 for IPv6. No forwarded header is read (`X-Forwarded-For` is
  ignored; the HTTP test sends one). The name's key is the first 32 hex characters of SHA-256 over `signin:` and the
  name lower-cased with trailing spaces removed, which is how the database (utf8mb4_unicode_ci) compares logins, and
  it is the same whether or not an account has the name.
- **Over a limit.** `login.php` checks the three limits before anything else. Over any one: the session message is
  "Too many attempts. Try again in N minutes." (N whole minutes until every limit holding it lets one more through,
  at least 1), the password is never checked (it is unset at once), a `signin_throttled` row is written, and the
  answer is the same 303 to `index.php` as a failure, with the recovery link beside the message while account mail is
  on. The same message for every case: wrong password, right password, unknown name, another case of the name.
- **What is not counted or cleared.** `signin_throttled` rows count against no limit, so a throttled visitor does not
  extend the wait. A successful sign-in clears nothing. The admin's manual password reset and the user editor are
  unchanged.
- **The settings.** A new Game Settings section, "Sign-in Limits", with the three numbers. They are bounded settings
  (`lib/settings.php`, `resurrection_bounded_settings()`): the field is a number input with its bounds, a stored value
  outside them is read as the nearest end, and each field's note says the range, the default and why
  (`lib/typed_editor.php`). The fresh install stores the defaults. The account limit is high on purpose: lower, anyone
  could keep a player out by failing on purpose; the pair and address limits stop one guesser long before it.
- **An unknown name.** `resurrection_sign_in_check()` (`lib/accounts.php`) always checks a password: against the
  account's hash, or, for a name no account has, against `RESURRECTION_SIGNIN_DUMMY_HASH`, a bcrypt hash of a random
  password at `PASSWORD_DEFAULT`'s cost (12 on both supported PHP versions; `SignInThrottleTest` holds it to
  `password_hash()`'s). A locked account's hash is checked too. A name that is not 1 to 50 printable ASCII characters
  is looked up nowhere (no login can hold one, and the collation would fold accents onto a login). Until this task an
  unknown name skipped the check and answered in a small part of a wrong password's time.
- **Keeping `faillog`.** Daily maintenance (`lib/newday/newday_runonce.php`, after account mail's cleanup) deletes
  every `faillog` row older than 30 days: sign-in's and `setup.php`'s, whose own count looks back 15 minutes.
- **Other counts stay their own.** `setup.php` keeps its 10 failures in 15 minutes per token file (its own `faillog`
  words, keyed by the token file), and account mail keeps its limits in `account_mail_log`. Neither reads the sign-in
  rows, and sign-in reads only `invalid_credentials` rows.

1.1.2 had no throttle: on a failure for an existing login it wrote the whole POST, the address and the `lgi` cookie
to `faillog`, and after 10 such failures from one address in a day it banned the address and mailed the staff
(`login.php` at the historical tag). Resurrection had removed that path before rc.1 (one fixed row, no ban). This task
adds no ban and no mail.

## Item 3 (N1): versioned asset URLs

- **The game's own links.** `\Resurrection\Ui\AssetUrl` (`src/Ui/AssetUrl.php`, new): `versioned($path)` returns the
  path with `?v=` and the first 12 hex characters of the SHA-256 of the file's bytes, computed once per request and
  kept in memory; a file that cannot be read keeps its plain URL. `rewrite($html)` versions every `href` or `src` that
  names a stylesheet or script under `assets/ui/` and leaves every other URL alone. `prepare_template()` runs it over
  the template after the template's checks and the safe frame choice, so the checks still read the file as written.
  `lib/output.php` (`showform.js`, `behaviors.js`) and `lib/pageparts.php` (`keys.js`, `tabs.js`) call `versioned()`.
- **The URLs inside the stylesheets.** The server sends a stylesheet as it is, so `resurrection.css`'s two `@import`
  lines and `fonts.css`'s sixteen font files carry the version written into the file by `scripts/asset-versions.py`
  (new; `--check` exits 1 and names each stale file). It writes in order, fonts into `fonts.css` first, then
  `fonts.css` and `tokens.css` into `resurrection.css`, so a changed font changes `fonts.css`, which changes
  `resurrection.css`, whose new version every page links.
- **The Content Security Policy** is unchanged: the URLs stay relative and on the game's own origin (`'self'`). The
  browser check shows every document enforced with 0 violations.
- **Images keep plain URLs.** The art is fixed at `1.0.0` (no new art after it, Jim's decision of 2026-11-13); a stale
  image breaks nothing; the host guide tells hosts to let browsers revalidate images. The host guide's upgrade section
  now says hosts may cache `assets/ui/` and `assets/fonts/` for a long time (the review's N1 asked for that
  recommendation).

Rendered, for example: `<link rel="stylesheet" href="assets/ui/resurrection.css?v=…">`,
`<script src="assets/ui/behaviors.js?v=…" defer></script>`, and in `resurrection.css`
`@import url('fonts.css?v=e9d8b6daabb6');` and `@import url('tokens.css?v=5e7eb30da5ad');`.

Files: `src/Ui/AssetUrl.php`, `lib/template.php`, `lib/output.php`, `lib/pageparts.php`, `scripts/asset-versions.py`,
`assets/ui/resurrection.css`, `assets/ui/fonts.css`, `docs/HOST-GUIDE.md` (`scripts/asset-versions.py` in the files
not uploaded; caching in section 9).
