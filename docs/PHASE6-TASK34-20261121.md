### Does `-dev` sort after `1.0.0` everywhere?

By SemVer precedence `1.0.0-rc.5` < `1.0.0` < `1.0.1-dev` < `1.0.1`. To find every place the project compares
versions, the code was searched for `version_compare`, `Version::`, `CURRENT` and the version patterns:

- **`scripts/release-upgrade-check.py`** is the only comparison of Resurrection versions. `precedence()` orders release
  tags, and a release sorts after its own test builds. A `-dev` version is never a tag, and `RELEASE_TAG` does not
  match one (`test_release_upgrade.py` refuses `v1.0.0-dev`). So a `1.0.1-dev` build is always compared as a commit
  after `v1.0.0`, never as an older version.
- **Whether a database needs an upgrade** is decided by its applied steps (`lib/upgrade.php`), never by the version
  string.
- **`lib/modules.php`'s `module_compare_versions()`** compares a module's own version, not Resurrection's.
- **The release cut workflow** and the validator match the version's shape; they do not compare versions. The
  workflow refuses a `-dev` version in Preflight.
- **`Version::CURRENT` is otherwise only shown** (`home.php`, `lib/pageparts.php`), and it names the documents' Git ref
  (below).

`docs/VERSIONING.md` has a new subsection, "Ordering", that says this.

### Found and fixed: the document links on a `-dev` version

- **The defect:** the pages that send an operator to a document link it at `blob/v` plus `Version::CURRENT`
  (`resurrection_doc_url()`, Phase 6 task 16, R2). Those pages are the not-installed page, "Upgrade Needed", "Game
  Unavailable", `setup.php`'s upgrade failures, `installer.php`'s 403, the shell commands' refusals and Game
  Settings' locked-setting note. Every version since task 16
  was a release or a test build, each with its own tag. At `1.0.1-dev` every such link would point at
  `blob/v1.0.1-dev/…`, and that tag will never exist, because `-dev` versions are never tagged.
- **The fix:**
  - `Version::docRef()` gives the ref: `v` and the version for a release or a test build, as before, and `main` for a
    `-dev` version. `resurrection_doc_url()` uses it.
  - `scripts/build-release-package.py`'s `INSTALL.txt` follows the same rule. The release cut workflow never builds a
    `-dev` version, so no published package changes.
  - Every release or test build still links its own tag, so a cut's package and pages are unchanged. The `1.0.0`
    package built from `v1.0.0` would be the same bytes.
- **The decision card:** the choice was put to Jim, with three options: `main` while `-dev` (recommended, and done
  here), the last release's tag, or leaving the links at the `-dev` tag. Jim had not answered by the push, so the
  recommended option stands; it is one small change to revisit if he picks another.
- **The tests:**
  - `DocLinkTest` gets a new test, `testEachKindOfVersionLinksARefThatExists`: `v1.0.0`, `v2.3.4` and `v1.0.0-rc.5`
    for those versions, `main` for `1.0.1-dev` and `1.1.0-dev`, and no link on this version containing `-dev/`. Its
    URL test now works out the expected ref from the version itself.
  - `CommandLinkTest` and `UpgradeTest` build the expected host guide address with `Version::docRef()`.
  - The three web tests that check a page's host guide link (`test_operator_pages.py` twice, `test_web_application.py`
    twice, `test_account_verification_http.py` once) take the address from a new helper, `tests/tooling/doc_urls.py`,
    which applies the same rule to `src/Version.php`. The account mail check is now stricter: it checks the whole
    address and its `#11-mail` anchor.
  - `test_release_package.py` checks `INSTALL.txt`'s address with the same rule, and that no address contains
    `-dev/`.
- **Fail-first:** this commit's tree, with `lib/source_link.php` and `scripts/build-release-package.py` as at

### A `-dev` tree has no release notes of its own

`test_release_package.py`'s `test_the_documents_are_beside_upload` required `RELEASE-NOTES-<version>.md` beside
`upload/`. At `1.0.1-dev` no such file exists: the brief says not to start `docs/RELEASE-NOTES-1.0.1.md` here, and a
`-dev` version is never cut.

The test now makes that requirement for a release or a test build, as before. For a `-dev` version it checks instead
that no notes file of that name exists. This keeps what the test protects, because a cut's version is never `-dev`:
the release cut workflow refuses one, and its publish step reads `docs/RELEASE-NOTES-<version>.md` at the tag. So the
bug-fix release's version commit, which sets `1.0.1` and writes `RELEASE-NOTES-1.0.1.md`, is held to the full check
again.
