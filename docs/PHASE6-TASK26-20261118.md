## R12: the training yard after the rollover

What Jim saw: the village's training link, the yard; the game day rolled over; he signed in again, and the page was the
yard with its Challenge form. Challenge answered the bare 409 "Training unavailable. Stored state was preserved. Reload
for a fresh form, or request operator repair if state remains invalid.", with no link.

Reproduced at `8aa67b8` (the probe's output is in `/mnt/project-files/phase6-task26/probe-8aa67b8.txt`):

- The sign-in goes 303 to `village.php`; the kept yard does not allow it, so 302 to `badnav.php`, which replays the
  kept page: the yard with its Challenge form. Challenge: 409, the bare text above.
- 1.1.2's `train.php` called `checkday()` on the yard, its Question page and the level-15 page, and its `login.php`
  redirected to `restorepage`, so a yard kept from the old day began the new day. Resurrection's yard never called it,
  and `badnav.php`'s own `checkday()` check reads the session's copy of the page, which `page_footer()` always clears
  (dead code, in 1.1.2 too).
- With a master fight stored at the rollover, the new day reset `seenmaster`, and Resurrection accepts a stored master
  fight only while `seenmaster` is set: every page of the fight answered the same bare 409.

The fix:

1. **Every training GET begins a due new day first** (`resurrection_training()`, `lib/training_combat.php`), before
   the training state is checked, through `resurrection_checkday_on_rollover()` (`lib/datetime.php`): when
   `resurrection_day_rolled_over()` holds, `checkday()`, which keeps the page as the return page and sends the player
   to the new day; else the page leaves `checkday()`'s mark, `<!--CheckNewDay()-->`. Nothing is spent. The new day's
   Continue returns to the yard. `resurrection_day_rolled_over()` is `is_new_day()` without its onboarding test: an
   unfinished race, specialty or Dragon Point choice is not a rollover, and its yard shows as before (its Challenge is
   refused, as `test_training_entry_authority_and_stale_round` pins). A POST page of the yard (a round) carries the mark
   too.
2. **The sign-in begins it too.** `badnav.php` now reads the kept page itself (`accounts_output`): when it carries the
   mark and the day has rolled over, `checkday()` runs before the replay. `checkday()` no longer records `badnav.php`
   as the return page (it would send Continue to the village); the return page stays the kept page's address, so the
   Continue goes back to it.
3. **A Challenge or autochallenge POST after the rollover** (from a page loaded before it) is refused before its action
   token is used: `resurrection_require_post()` (CSRF), then the framed 409 "Training unavailable. ..." with one way
   out, "Begin the new day", to `train.php`, whose GET begins it. Nothing is spent; `seenmaster` is not set. The check
   inside the mutation (`is_new_day()`) stays as the second guard.
4. **The master fight stored at the rollover: the DO 3 choice.** The new day leaves `seenmaster` set while a master
   fight is stored (`resurrection_newday_master_fight_kept()`, `lib/newday_daily.php`: `badguy` not empty,
   `seenmaster` 1, and the stored state's `options.type` `'train'`; both reset lines in
   `lib/newday_daily_outcomes.php`). The kept fight is that day's challenge: it shows as it was, plays to its end, a
   victory resets `seenmaster` (multimaster) as before, and after a loss there is no second challenge that day. Why:
   - no dead end: the fight shows and plays on;
   - nothing unearned: the player gets the one challenge every day gives, not two;
   - the rule that a stored master fight needs `seenmaster` set stays, so a fight with `seenmaster` 0 is still invalid
     stored state (`test_user_editor_stored_state_repair_http` offers its repair).
   The other choice, accepting a stored master fight with `seenmaster` 0, would weaken that check and give a second
   challenge after a loss. 1.1.2 kept the fight (its `op=fight` never read `seenmaster`) and its new day also opened a
   second challenge; that difference is recorded in `docs/CHANGES-FROM-1.1.2.md`.
5. **Every training refusal goes through `resurrection_refuse_page()`** (`resurrection_training_refuse()`), keeping
   its status and message, in the game's frame with the credits, and one way out
   (`resurrection_training_way()`), which `resurrection_refuse_page()` also makes the return page, so the next sign-in
   comes back to it:

| Refusal | Status and message | One way out |
|---|---|---|
| `lib/training_combat.php`: a request `Input::choice()` or the POST check refuses | 400 "Invalid training action." | the rollover: "Begin the new day" (`train.php`); a master fight stored and valid: "Return to the fight" (`train.php?op=fight`); training works for the player: "Return to the training yard" (`train.php`); else the village, or the Shades for the dead |
| `lib/training_combat.php`: the training state refused (dead, an event, invalid stored state), Challenge unavailable, not truant, stale, a Challenge after the rollover | 409 "Training unavailable. Stored state was preserved. Reload for a fresh form, or request operator repair if state remains invalid." | the same order |
| `lib/training_combat.php`: a caught failure (one error-log line, `FailureLog`) | 500 "Training action was not completed. Request a fresh form." | the same order |
| `train.php`, while `common.php` loads: a `DomainException` | 409 "Invalid stored training state. Stored state was preserved." | the same order, when the page got as far as forced navigation (`resurrection_refusal_framed()`); else the plain text |
| `train.php`, while `common.php` loads: any other failure (one log line) | 500 "Training could not be loaded. Stored state was preserved." | the same |
| `train.php`, before `common.php`: a parameter other than `op` and `c` in the query, or other than `csrf_token`, `action_token` and `rounds` in the form | 400 "Invalid training action." | none: plain text, as before. There is no session, frame or player yet |

`train.php`'s load-time catches now record the refusal and, at global scope, frame it through
`lib/training_combat.php` (global scope because `lib/battle_view.php` keeps its battle screen in a top-level
variable). The load-time 500 is tested by taking the `clans` table away for one request (`common.php` reads it after
forced navigation). The load-time 409 is framed by the same code; no player state the tests could build reaches it
(`common.php`'s own stored-state checks answer themselves), so it has no test of its own.

## R13: after a special ability

What Jim saw: in a forest fight, Dark Arts' Skeleton Crew pressed on the battle screen led to a page with only
Continue; Continue went to `forest.php?op=specialty`, whose GET showed only the abilities with uses left; after the
day's last use, a page with no form and no link.

Reproduced at `8aa67b8` (the probe): the first round's page had the one ability form left and the one nav
`forest.php?op=specialty`; after the last use, no form and that one nav; its GET, no form and no nav.

The fix (`lib/specialty_combat.php`, `lib/forest_combat.php`, `forest.php`):

1. The round's page (the POST) is the forest fight, as the ordinary Fight round shows it: `page_header('The Forest')`,
   the enemies (`battle.php`), and `resurrection_forest_round_navs()`, which the Fight round now calls too: while the
   fight goes on, `resurrection_forest_forms()` (Fight, Run, autofight where `autofight` and `autofightfull` allow it,
   and the abilities with uses left); after its end, the outcome and the forest's navs ("The Forest", "Return to the
   village"); during an event, the event's own. No Continue. 1.1.2 ran an ability inside the fight's round
   (`forest.php?op=fight&skill=..&l=..`, `fightnav()`), so this is 1.1.2's page.
2. The GET of `forest.php?op=specialty` (an rc.4 page's Continue, the return page, a replay) shows what `forest.php`
   shows: the stored fight (the `fight` route, its GET presentation only) or, with none, the forest. Nothing is spent.
   Its refusals keep task 24's framing.
