## 2. Stale form tokens after signing in again

### Reproduction (fails first at `3dba4d1`)

`tests/tooling/test_web_application.py`:

- `test_relogin_during_newday_questions_continues_the_day_http`: a new player (race and specialty modules on) is at the
  race question; the session times out (its `laston` two hours back); they sign in again and land on `badnav.php`, which
  shows the race page again. At `3dba4d1` its form answers **403 "Invalid form submission."**:

  ```
  FAIL: test_relogin_during_newday_questions_continues_the_day_http
  AssertionError: 200 != 403 : Invalid form submission.
  ```

  With the fix it answers 200 and the race is set. The same for the specialty question after an explicit sign-out, and
  for the New Day page after a timeout; then the day runs and the village link works.
- `test_relogin_mid_fight_keeps_forms_working_and_old_tokens_refused_http`: a forest fight's form, the same session
  (the replay holds the same tokens), then a timeout and a new sign-in. At `3dba4d1`: `200 != 403 : Invalid form
  submission.`; with the fix the replayed Fight button fights.
- `tests/unit/KeptPageTest.php` (5 tests): the kept copy holds markers and no token; the same session gets its page back
  byte for byte, and a used action token is not issued again; a new sign-in gets fresh tokens and the old ones stay
  refused; damaged markers and copies kept before this change; the user editor's view shows no token. At `3dba4d1` it
  cannot load (`src/Security/KeptPage.php` does not exist).

### Cause

`page_footer()` keeps the page it sends (`$session['output']`, saved to `accounts_output`) so that `badnav.php` can show
it again when the next request is not one the page allowed. 1.1.2's forms had no tokens, so the copy worked in any
session. Resurrection's forms carry the session's CSRF token and one-use action tokens (`ActionToken`, bound to a hash
of the state they were issued for). Signing in rotates the session: a new CSRF token and no action tokens. The restored
`allowednavs` still name the page's links only, so the next page is `badnav.php`, which echoed the copy with the
earlier session's tokens: every form answered 403. Even with a fresh CSRF token, the action tokens were gone, and five
contexts included `authversion`, which every sign-in increments, so a token issued for the replayed page would not
match the state at submission either.

### Fix

- `src/Security/KeptPage.php`: `keep()` replaces the session's CSRF token in the copy with a fixed marker and each action
  token with a marker that names its scope and context (hex of the JSON pair; never the token). `replay()` fills the
  markers from the session that shows the page: its CSRF token; the action token it holds for the same scope and
  context, if any; only on the first replay after signing in (`$_SESSION['kept_page_reissue']`, set by `login.php` and
  cleared by the next `page_footer()` or replay), a fresh token for that scope and context; otherwise an empty value,
  which is refused as an expired action as before. A copy kept before this change (tokens, no markers) is shown as it
  is, so its forms are refused as before. `view()` empties the markers for the user editor.
- `lib/pageparts.php`: `page_footer()` keeps `KeptPage::keep()` of the secret-masked copy, on the line after the one
  `SecretPageTest` pins (that line is unchanged; the test now pins the second line too).
  `$_SESSION ?? []`: the setup page draws its screens through `page_footer(false)` and has no session before a grant,
  so its HTTPS refusal screen (403) came out empty with `$_SESSION` alone. The first local shard run caught it
  (`test_setup_refuses_plain_http` and `test_setup_forwarded_proto_trusted_only_with_the_third_line`: "1 != 0" for
  the copyright line on an empty 403 body); with the guard all 15 `SetupPageTests` pass. `badnav.php` echoes `KeptPage::replay()`.
  `lib/user/user_lasthit.php` echoes `KeptPage::view()`.
- `login.php`: after the session is rotated it drops any action tokens and sets the one reissue. The sign-out
  confirmation page is not kept (`page_footer(false)`), so after signing in again the page shown is the one the player
  left.
- `authversion` left out of the action contexts of training, the inn room, the dragon fight, dragon points, the
  graveyard and the new day. Within a session it cannot change: a request whose account no longer matches the
  session's `authversion` ends the session (`lib/forcednavigation.php`). Each list carries a comment saying why.

### Old tokens stay refused

The tests submit the earlier session's form after the new sign-in: 403 "Invalid form submission." (its CSRF token is
not the session's), and with the new CSRF token but the old action token: 409 "Expired or repeated action." (the session
holds a different token for that scope). The state is unchanged after each (race, specialty and `lastnewday` empty; the
fight's state the same). A used replayed token is refused (409). No token is ever issued that is not in the session:
the reissue happens once, for the scopes and contexts the kept page names, and context still binds the token to the
exact state. CSRF validation (`Csrf::valid`, `hash_equals`) is unchanged.

Guard variants, each run on the HTTP tests and each failing: without `login.php`'s reissue the replayed form has
`action_token value=""` and is refused; with `authversion` back in the new-day context the New Day form answers
`200 != 409 : Expired or repeated action.`.

`badnav.php` shows the kept page whenever the next request is not one its links allow. After signing in that is any page
whose links do not include `village.php`, the sign-in's landing page. Pages with forms among them:

|---|---|---|
| New day: race question (`newday.php`, race modules) | race choice (`race-onboarding`) | HTTP test |
