## 2. R10: what Jim saw

Jim's server, upgraded from rc.1 to rc.2. His administrator character had hit R6's 500 (the Dark Horse Tavern exit,
fixed in task 20) the day before. On rc.2 he entered and left the tavern, then pressed "Look for Something to Kill". He
got a bare text page, "Expired or repeated action.", with no frame and no link, and every request brought him back to
it. He left only through the Grotto and "Return to the Mundane", which only an administrator has.

## 3. Reproduction

Both reproductions ran over HTTP against real installs: the published rc.2 package (`100103d`) served by PHP 8.5's
server as `nobody`, with MySQL 8.4, through a scripted cookie client and through Chromium.

- **(a) A clean rc.2 character.** A fresh rc.2 install; a plain player (no superuser rights) made through the
  sign-up, played to the village, then forest, the Dark Horse Tavern (forced as the forest event), Exit,
  Leave the tavern, then "Look for Something to Kill" and every other forest link.
  - With no day change: every forest link worked, in both clients. Not reproduced.
  - With the game day rolled over while the player was in the tavern (the player's `lastnewday` moved back one game
    day): reproduced exactly. The search link showed its form (200); pressing it answered a plain 409, "Forest combat
    unavailable. Stored state was preserved; reload for a fresh form, or request operator repair if it remains
    invalid."; every later page (village, forest, inn, stables, badnav.php) answered 200 with that same search form
    from badnav.php, and pressing it answered a plain 409, "Expired or repeated action.".
- **(b) The R6 leftover state.** A fresh rc.1 install (the published rc.1 package); the administrator played the Dark
  Horse Tavern's stones game and left: R6's 500 (`Class "Resurrection\Game\StonesState" not found`, in the error log).
  The database was then upgraded with the rc.2 package's `scripts/upgrade.php` (steps `0002` and `0003`; this commit
  adds no step, so the upgraded rows are the same at this commit). Signing in lands on the kept tavern page.
  - With no day change: Exit, Leave the tavern and the search worked. Not reproduced.
  - With the day rolled over: the same loop as (a), word for word. Run again for this record on the rc.2 code:
    `Leave the tavern` 200, `Look for Something to Kill` (link) 200, the button 409 "Forest combat unavailable…";
    then `village.php`, `forest.php`, `inn.php`, `badnav.php` each 200 at `badnav.php` with the search form, and the

So both reproduce it, and only with the rollover. The R6 state is incidental: it put Jim in the forest when he signed
in, past the village. No stored row is wrong in either state, so there is nothing to recover and no upgrade step.

## 4. The cause

- The trigger: the game day (6 hours by default) rolled over while Jim was in the forest. He came in through the kept
  tavern page and never passed the village, whose page runs `checkday()` and starts a due new day.
- The search form never checked the day. `resurrection_forest_combat()` (`lib/forest_combat.php`) showed the form on
  the GET of `forest.php?op=search`. On its POST it called `resurrection_consume_action('forest-search', …)`, which
  spends the form's one-use action token, and only then refused the search because the new day had not begun
  (`DomainException`, plain 409 "Forest combat unavailable…").
- The refusal saved nothing, so the allowed navigation and the kept page (`accounts_output`) still held the search form
  page. Every request outside those navs went through `do_forced_nav()` to `badnav.php`, which replays the kept page.
  Its form carried the spent action, so every press was refused by `resurrection_consume_action()` as a stale action:
  plain 409 "Expired or repeated action.". The only allowed GET was `forest.php?op=search`, which drew the same form
  again. That is the loop.
- 1.1.2 did not have it: its `forest.php` ran `checkday()` for `op=search` (line 56 at `historical-source-1.1.2`), so a
  due new day sent the player to `newday.php` first.

## 5. The fixes

### The cause (`lib/forest_combat.php`)

- A new `resurrection_forest_day_rolled_over()`: whether the game day has rolled over since the player's last new day
  (`lastnewday` against today's game date; `is_new_day()` for an account with no marker). It leaves out the onboarding
  test that Resurrection's `is_new_day()` adds (no race or specialty), which is not a rollover.
- A search after the rollover:
  - GET (the search link, Slumming, Thrillseeking, Suicidally) runs `checkday()`, as 1.1.2 did: 302 to `newday.php`,
    and the search page becomes the page restored after the new day.
  - POST is refused before anything is spent: `resurrection_refuse_action(409, …)`, the framed refusal below.
- The old check after the token is spent stays, for unfinished onboarding. The first local run of shard 1 failed
  `test_ordinary_forest_search_escape_and_event_handoff` (GET 302, expected 200) when the new check used `is_new_day()`:
  that test pins the search form for a player with no specialty. Narrowing the check to the rollover keeps it as it was;
  the test was not changed.

### The dead end (every player)

- `resurrection_refuse_action(int $status, string $plain)` (`lib/web_security.php`) answers a refused action (409)
  or form (403):
  - The status code is unchanged, with `Cache-Control: no-store`. The refused action still does nothing, and the stale
    token is still refused: nothing is consumed or written other than what is listed here.
  - On a game page (one that passed `do_forced_nav()`, signed in, with `page_header()` loaded, headers not sent, not
    `newday.php`) it answers in the game's frame: the title "That action has expired", the message "That action has
    expired. Nothing was changed.", the template's credit line, license block and attribution line, and no other
    content (the page's output and navs are cleared first).
  - After a 409: the page's one link is back to the village (or the Shades for the dead); the navs the last page
    allowed stay allowed, with that link added; the return page (`restorepage`) becomes `village.php` or `shades.php`;
    and this page is kept (`accounts_output`). So `badnav.php` replays the refusal, never the refused form, and a later
    sign-in returns to it too. Only `allowednavs`, `restorepage` and the page timing columns are written:
    `saveuser()` honors `RESURRECTION_REFUSAL_PRESENTATION` as it does `RESURRECTION_NEWDAY_PRESENTATION`.
  - After a 403 (a form the session did not issue): one link, "Return to the game" (`badnav.php`), and nothing is
    saved (`page_footer(false)`); the kept page's one-time reissue flag is put back if it was set.
  - Anywhere else: the plain text as before (`Expired or repeated action.` or `Invalid form submission.`).
- Callers: `resurrection_consume_action()` (`lib/player_mutation.php`), `resurrection_require_post()`
  (`lib/web_security.php`) and the user editor's stale snapshot (`lib/user_editor.php`).
- `do_forced_nav()` (`lib/forcednavigation.php`) marks a request it allowed (`$GLOBALS['resurrection_forced_nav_page']`),
  which is how the refusal knows it is on a game page.
- No security check is weaker: the CSRF check, the action token's single use and its context check, the forced
  navigation check and the status codes are as they were. The existing CSRF and action-token tests pass unchanged.

### Refusals left plain (not game pages, or plain by design)

- Pages outside the game's navigation (`OVERRIDE_FORCED_NAV`): `mail.php` (player mail, a popup), `motd.php`,
  `petition.php`, `translatortool.php`, `untranslated.php`.
- `account.php` (account mail links and recovery; its own fixed pages), `login.php` and `create.php` (signed out).
- `setup.php` (the operator screens; never loads `common.php`) and the commands; no JSON endpoint uses these helpers
  (`installer.php`, `cron.php` and `webcron.php` are untouched).
- `newday.php`: its questions are replayed with this session's tokens, and its 403 body is pinned to exactly
  "Invalid form submission." by an existing test (`test_web_application.py`, the new day's CSRF test).
- Any request refused before `common.php` has run.
- Other domain refusals (for example "Forest combat unavailable" for another reason, "Lovers is unavailable",
  "Event state changed") are not action-token refusals and keep their text; a press after one of them reaches the
  framed spent-token refusal, which has the way out. The graveyard search and training spend their action before their
  new-day check, as the forest search did; they were not changed (a graveyard test relies on that 409), and the framed
  refusal leaves them no dead end.

### Checked again on the R6 state with the fix

The (b) database, upgraded and rolled over as above, served with this commit's six `lib/` files: Exit, Leave the tavern,
then "Look for Something to Kill" answered 302 to `newday.php`, "It is a new day!". With the form shown before the
rollover and pressed after it: 409 "That action has expired" in the frame; `forest.php` then gave the same framed page
from `badnav.php`; "Return to Degolburg" led to the new day.
