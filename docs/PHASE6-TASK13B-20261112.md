## 1. `account.php`: forgot, open and reset (design 3.1 to 3.4)

Files: `account.php`, `lib/account_recovery.php` (new), `lib/pageparts.php`.

**The request, `op=forgot`.**

- GET, while account mail is effectively on: one field, "Login or email address", and CSRF.
- GET, while it is off: the one line from section 6, "Password recovery by email is not available on this game. Use
  Petition for Help to ask an administrator to reset your password."
- POST: a missing or wrong CSRF token gets the usual 403 and nothing is counted. Every other POST gets the same page:
  "If an account matches and can receive mail here, a message with a link is on its way. It works for 30 minutes.
  Check your spam folder too." The status (200), headers and cookies are the same in every case, malformed input
  included (over 128 bytes, a control character, an array, no field), and so is a POST made after account mail was
  turned off.

**After the response.** The page is rendered before any of the request's work runs, so nothing in it can depend on the
outcome. `account.php` holds the page in an output buffer, and a shutdown function sends it through
`resurrection_account_after_response()`:

- Where the server has `fastcgi_finish_request()` (PHP-FPM) or `litespeed_finish_request()` (LiteSpeed): the page goes
  out whole with `Content-Length`, the response is completed, and only then do the limits, the lookup, the token and
  the mail run.
- Where it has neither (mod_php, CGI, the built-in server): the work runs first, and the page is held until 1.5
  seconds after the request started, whatever the work took.
- The session is written and closed before the work, so it never holds the session lock. Anything the work prints is
  dropped, and a failure is one fixed line in the PHP error log, never its message.

**The work** (`resurrection_account_recovery_request()`):

1. The requester is counted (`recover-request`, 10 an hour per `REMOTE_ADDR` key); past the limit it is recorded as
   `limited` and goes no further.
2. Malformed input stops here (it was counted). With account mail off, it stops here too.
3. One lookup. A value with `@` is an address: every account whose `emailaddress` equals it, case-insensitively, and
   whose `emailverified` equals that address (decision 2), at most 5, the oldest first. Anything else is a login,
   matched exactly.
4. For each account, eligibility: a valid address verified for it; `locked` 0; no pending sign-up (`emailvalidation`
   empty); no ban on its last IP or ID (`checkban()`'s query, without its session and redirect; `banoverride` and staff
   accounts are never banned, as in `checkban()`); a staff account only while `account_mail_staff` is on.
5. The 5-minute rule: an account with a live recovery token made less than 5 minutes ago gets nothing new (recorded as
   `skipped`); the earlier mail stands.
6. The per-account (3 an hour, 6 a day), per-address (5 a day) and global limits; one reached is recorded as `limited`.
7. A token for each remaining account. A new recovery token marks the account's earlier ones used, so at most one
   recovery link per account works.
8. One mail to the address, "Choose a new password", listing each account's login with its own link from `serverurl`.
   It is recorded once per account it serves (each account's limits count it), with the address key on the first row
   only (the address received one mail). A refusal by the transport is recorded as `refused` with a game log line.

**The open, `op=open`.** As in 13a, with the recovery purpose accepted only while account mail is effectively on (a link
mailed while it was on gets the expired page after it is turned off). A recovery link answers 303 to
`account.php?op=reset`. Opening counts one open (at most 5) and never uses the token up; a link scanner's open makes a
grant in the scanner's own session and nothing else.

**The reset, `op=reset`.**

- GET: with a live recovery grant whose token is still live (unused, unexpired, the account's `authversion` still the
  token's), the form: two password fields (12 to 72 bytes) and CSRF, naming the account's login. Otherwise the expired
  page, and the grant is cleared.
- A visitor signed in as another account than the token's gets "Sign out first" on GET and POST, and nothing changes.
- POST with CSRF (`resurrection_account_recovery_reset()`): the passwords must match and pass `Passwords::hash()`;
  otherwise the form again with the reason, and the grant stands. Then one transaction: the token row `FOR UPDATE`
  (unused, unexpired, its hash the grant's), the account row `FOR UPDATE` (`authversion` still the token's, unlocked,
  still holding the address the mail went to, and for a staff account the switch still on), `UPDATE accounts SET
  password=?, authversion=authversion+1, loggedin=0 WHERE acctid=? AND authversion=?` (exactly one row), the token used,
  and every other live recovery token of the account used. Any failure rolls back and gets the expired page.
- Then the grant is cleared, the session rotated, and a game log line written ("Password reset through a recovery link
  for account N"). The page says "Your password was changed. Sign in with it now." The player is not signed in.
- After the page: the notice mail, "Your password was changed": "The password for <login> at <serverurl> was changed by
  a recovery link at <time UTC>. If you did not do this, ask for a new link or contact the game's administrator." No
  link and no IP. It counts against the address and global limits.

**The same page, byte for byte.** 13a's `account.php` footer showed the time to the next new day and the page-gen
timings, which differ between any two requests. `account.php` now defines `RESURRECTION_QUIET_FOOTER`, and
`page_footer()` then shows no next-new-day time and, of the page-gen line, only the query count ("Page gen: 79
queries"). The query count stays because 13a's `test_every_unusable_link_gets_the_same_page` compares it between
refused links (the same database work); every forgot-password answer is rendered before its work, so its count is the
same in every case.

Tests: `MailRecoveryTest` (all nine), `test_account_recovery_http.py` (all seven).

### Deviations from the design, and why

- **All of the request's work runs after the page, not only the mail.** The design sends only the mail after the
  response and accepts a token insert as the remaining difference. Running the limit counts, the lookup and the token
  after the page too removes that difference where the server can finish early, and makes the rendered page
  independent of the outcome everywhere. The 1.5-second floor stays where it cannot.
- **The footer.** The design does not mention it; without the change, two answers could never be byte for byte the same
  (section 1).
- **The reset rechecks more than the design lists**: the address the mail went to, and the staff switch, besides
  `authversion` and `locked`. A link mailed to an old address, or to a staff account after staff were excluded, cannot
  set a password.
- **`op=reset` GET checks the token too**, not only the grant, so a page opened after a sign-in, a sign-out or a
  password change shows the expired page instead of a form that would fail.
- **The design's index.php link** is on `home.php`, the page that shows the sign-in form (`index.php` only redirects to
  it).
- **Test names**: `AccountRecoveryTest` is `MailRecoveryTest`, so that it sorts after `FreshInstallTest` (as 13a did);
  the design's HTTP tests are in a new file, `test_account_recovery_http.py`, to keep 13a's file as it was.
- **Until 13c, only an administrator's address is verified** (by a confirmed test mail), so in practice a player cannot
  yet receive a recovery mail: decision 2 sends recovery only to verified addresses, and player verification is 13c.
